# Signature-encoding review, 3 November 2026

The review found and fixed three Falcon compatibility defects and tightened the proof-file decoder. It did not demonstrate a missing signature constraint that accepts a false signature relation under the intended registered key. That is a bounded review result, not a formal correctness certificate or a proof of signature security.

The [new size study](../results/size-growth/REPORT.md) uses the corrected Falcon guest and independently verified proof files. Earlier Falcon rows in `results/COMPARISON.md` remain historical measurements of the stricter pre-review guest, with their original program hashes. They must not be relabeled as measurements of the updated program.

## Corrections

| Item | Demonstrated failure | Fix and control |
|---|---|---|
| Falcon compressed-payload policy | A fully reconstructed, canonically encoded 640-byte payload with valid norm passed pinned C verification but failed the guest's invented 625-byte limit. | Removed the extra policy and length accumulator. Both 576-byte and 640-byte synthetic controls now pass C, Python and the guest. Coefficients beyond the decoder's 2047 bound still fail. |
| Falcon host decoder | One appended zero byte was accepted by Python while the pinned C decoder rejected the length-adjusted signed message. | Require exact consumed byte count while allowing only final-byte zero padding. A deterministic 440-case differential corpus agrees with C. The existing fixture builder's complete C check already prevented this disagreement from admitting an invalid fixture. |
| Falcon empty messages | C and Python accepted a valid empty-message signature, while guest compilation failed on a zero-cell hash input. | Added an explicit zero-length hash case. C/Python/VM agreement now covers empty messages. Nonempty compiled bytecode and the new size-study proofs are unchanged by this fix. |
| Proof-file transport | The generic bincode decoder accepted a valid proof plus an arbitrary unparsed trailer. | Require fixed-integer encoding and exact consumption. Valid saved proofs pass; appended bytes and corrupted proof contents fail. This closes a serialization-malleability issue; no signature forgery was demonstrated. |

Reproduction, before/after evidence and scope are in [the Falcon review](../review/falcon/REPORT.md), its three finding JSON files and [the strict saved-proof checks](../review/fors/verify-results.strict.json). The compatibility witnesses use canonical synthetic keys to isolate the verifier relation; they are not claimed to arise from honest key generation or to forge an honest registered key.

## Constraint checks

Three independent reviewers examined each signature relation and the host binding. The method combined direct source reasoning, native differentials and adversarial executions with a predetermined accepting or rejecting control.

- **Falcon:** independently constructed polynomial equations exercise the full NTT and norm checks. Fully recomputed witnesses accept coefficient magnitude 2047 and reject 2048 despite a valid norm. Twelve attacks replace computed bit advice with arbitrary witnesses, preserving the exact compiled program hash, then inject non-Boolean or extension-field values across every decomposition category. All reject at Boolean constraints. Quotient, rejection-sampling and norm attacks from the regression suite remain rejected. [Detailed evidence](../review/falcon/REPORT.md).
- **Dilithium:** exhaustive integer enumeration covers all 8,380,417 rounding residues and agrees with pinned C. Relaxing the forbidden negative tie introduces 43 duplicate encodings, a discriminating control. Actual VM tests cover 616 rounding boundary outputs, all 256 one-bit message positions plus zero/all-one messages, native packing across all 44 high values, norm endpoints and hint populations 80/81. Differentials cover 100 NTT/inverse vectors, 512 native challenges, 20 chunked PRNG streams and 80 matrix samples. Fully recomputed false signatures fail at the final challenge equality. [Script](../review/dilithium/grind.py), [recorded results](../review/dilithium/report.json).
- **FORS:** independent byte-level trees and commitments cover multiple supported parameter sets and multi-record batches. Replacing computed limb/bit hints with arbitrary witnesses preserves the compiled guest hash. Wrong limbs, wrong digest bits, extension-field bits, wrong paths and changed claims with recomputed batch digests all reject. Canonical header cells, path directions, tree/height/index addresses and final forest-root equality were traced through the compiler and memory interface. Thirty-eight execution outcomes matched their controls. [Detailed evidence](../review/fors/REPORT.md).

The integer-in-the-exponent representation needs explicit ranges to prevent group-order aliases. The largest reviewed Dilithium multiplication intermediate is below 70,300,024,700,928, versus generator order `2^64-1`. Falcon coefficient products and complete norms are also far below that order. A separate deterministic check verifies all seven prime-divisor conditions for the generator's full order under the upstream field arithmetic: [record](../review/generator-order.json).

Exhaustive rounding enumeration is a check of the integer relation against C. The actual VM was tested at boundary vectors, not exhaustively at every residue. Interpreter rejection and source tracing do not independently establish the soundness of every possible malicious execution trace or proof.

## Public statement authentication

The proof binds the actual program and its two public-input cells. Guest code computes the ordered key/message commitment; verification of the supplied source does not authenticate the intended wallet operation by itself. Scheme names, benchmark counts in metadata and other labels are not signed or proof-bound. The count is fixed by the expected guest specialization, not by an unauthenticated metadata field.

The runner now exposes `--expect-guest-hash` and `--expect-public-input`; both must match for `statement_pinned=true`. The expected values must be derived from trusted local circuit configuration and intended key/message claims. Copying them from a received artifact supplies no authentication. Wrong pinned values fail. Generic unpinned verification intentionally remains available for arbitrary execution-proof experiments and reports `statement_pinned=false`. Dependency export carries the same distinction.

## Remaining semantic and security limits

1. **Dilithium compact-key consistency is not proved.** The guest authenticates the registered expanded `(A_hat,t1_hat,tr)` digest. It does not prove expansion from the 1,312-byte compact key. The reviewer constructed a zero expanded matrix/key that accepts signatures for two messages without a secret; those signatures fail under the original honest compact key and have a different expanded key digest. This confirms why registration must validate and authorize the expansion. It is not an honest-key forgery. A consumer needing compact-key semantics must add or validate that bridge.
2. **Raw signature bytes are not the public claim.** The lattice guests prove existence of bounded, canonically encodable decoded signatures for the committed key/message relation. They do not authenticate a supplied signature byte string or its identifier. That distinction is suitable for signature-eliding aggregation only when the consumer intentionally adopts this relation and key codec.
3. **The standalone FORS variant is weaker than a full wallet signature.** It deterministically exposes `k*a=128` message-index bits without a signer-controlled randomizer. Two chosen messages sharing that vector accept the same signature. In an ideal-hash model a birthday search costs about `2^64` hashes before one signing query. A reduced-parameter example demonstrates the exact signature-transfer relation with a rejecting different-index control; the default complexity is an analytic bound, not a completed `2^64` attack. Consequently the backend's target security does not confer 128-bit chosen-message security on this research variant. Use a separately analyzed complete signature construction for a wallet, including its randomization and key-authentication requirements. [FORS details](fors.md); [FIPS 205 describes FORS as a component of SLH-DSA](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf).
4. **Bounded samplers restrict completeness.** Falcon permits 40 counter blocks; Dilithium permits 120 challenge candidates and fixed 32-byte messages with empty context. A valid instance outside those bounds cannot be proven by these guests. No invalid acceptance was demonstrated from the caps.
5. **System integration remains outside this review.** A later [fixed-arity ETHFALCON recursive experiment](../results/recursive-30/REPORT.md) is now implemented and separately [reviewed](recursive-envelope-review.md). Arbitrary multi-level recursion, compact-key registration logic, EIP-8141 transaction/policy validation, full EIP-8288 client integration, threshold signing and hardware-wallet signing remain outside these signature guests. Current backend proofs are not zero knowledge.

## Validation and boundary

At this encoding-review snapshot, 30 regression tests passed after the corrections; later recursion work adds separate tests. `cargo clippy --release --locked --all-targets -- -D warnings` passed. All 36 size-study proofs (5 Falcon, 1 Dilithium, 30 FORS) passed fresh native verification. Independent review scripts provide additional differential/adversarial evidence; they are not counted as the regression-test total. Strict saved-proof transport tests passed all six controls.

Two additional real Falcon proofs cover the formerly rejected 640-byte-payload signature and the formerly uncompilable empty-message signature. Both pass the pinned C verifier and fresh proof verification with expected program and public-input pins. Their outcomes are recorded in [proof-regressions.json](../review/falcon/proof-regressions.json); their proof files and witness-free statements are under `artifacts/encoding-review/`. These are positive compatibility regressions, not proofs of unforgeability.

This work did not formally verify or comprehensively audit leanVM's compiler, all frame/allocation aliasing choices, memory buses, Keccak GKR, Fiat-Shamir/PCS arguments, or native verifier as a whole. It does not prove the cryptographic unforgeability of the ETH variants or this standalone FORS construction. The supported conclusion is that the exercised guest relations have explicit enforced checks with no demonstrated missing signature constraint, after the compatibility corrections above, subject to the stated key and protocol boundaries.
