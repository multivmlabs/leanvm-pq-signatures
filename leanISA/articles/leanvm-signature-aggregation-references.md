# Checked primary references

Checked on 3 November 2026. Draft EIPs and repositories can change; algorithm pins for the experiment are recorded separately in [upstream.lock.json](../upstream.lock.json).

- [Recursive-STARK-based bandwidth-efficient mempool](https://ethresear.ch/t/recursive-stark-based-bandwidth-efficient-mempool/23838), Vitalik Buterin, 12 January 2026. Source for merging valid objects and recursive proofs while maintaining an explicit object set and permitting discards. Our ordered deterministic trees do not implement its union/discard protocol.
- [Signature Merging for Large-Scale Consensus](https://ethresear.ch/t/signature-merging-for-large-scale-consensus/17386), George Kadianakis, Dmitry Khovratovich, Zhenfei Zhang and Mary Maller, 10 November 2023. Source for the signer-set/bitfield merge problem and proof-carrying aggregation motivation. It is not a benchmark of this implementation.
- [EIP-8141: Frame Transaction](https://eips.ethereum.org/EIPS/eip-8141), current draft. Account validation and canonical signing interface. The ARBITRARY route exposes signature bytes to introspection; it does not itself supply aggregate witness removal.
- [EIP-8288: In-mempool signature and proof aggregation](https://eips.ethereum.org/EIPS/eip-8288), current draft. Generic leanSTARK scheme 0x11 remains reserved; protocol verification constants are unfinished. Current mode-1 rules include transaction/dependency equality. We do not repeat the older missing-equality objection as an unresolved current-spec defect.
- [Generic batching proposal, reply #14](https://ethereum-magicians.org/t/eip-8288-frame-type-for-pq-sig-and-stark-aggregation/28723/14), zsfelfoldi, 1 November 2026. Proposes same-verifier batches with per-item public dependencies and raw witness admission. The body was verified through the [indexed full discussion](https://ethereum-magicians.org/t/eip-8288-frame-type-for-pq-sig-and-stark-aggregation/28723) because the direct numbered URL failed to load in the research tool.
- [Reply #13](https://ethereum-magicians.org/t/eip-8288-frame-type-for-pq-sig-and-stark-aggregation/28723/13), ArikG, 19 October 2026. Discusses hiding classical signatures behind proofs. We do not infer post-quantum unforgeability of ECDSA/EdDSA from a hash-based wrapper: the underlying signature acceptance relation still matters.
- [FIPS 204: Module-Lattice-Based Digital Signature Standard](https://csrc.nist.gov/pubs/fips/204/final), NIST, 13 August 2024. ML-DSA naming and verification specification. The publication page lists an errata planning note dated 31 July 2026; the experiment pins its actual source implementation.
- [CRYSTALS-Dilithium round-3 specification](https://pq-crystals.org/dilithium/data/dilithium-specification-round3.pdf). Historical algorithm specification, distinct from FIPS 204 ML-DSA. The experiment does not present the ML-DSA-era source as round-3 Dilithium2.
- [Efficient Threshold ML-DSA](https://www.usenix.org/system/files/conference/usenixsecurity26/sec26_prepub_celi.pdf), Sofía Celi, Rafael del Pino, Thomas Espitau, Guilhem Niot and Thomas Prest, USENIX Security 2026 prepublication. A concrete standard-compatible threshold signing construction with its own implementation and communication evaluation. It is neither an audited wallet deployment nor a threshold implementation measured by our project.
- [Thresholdizing Standardized FALCON Signatures](https://eprint.iacr.org/2026/1300), Radhika Garg, Daniel Escudero, Antigoni Polychroniadou, Akira Takahashi and Xiao Wang. Demonstrates threshold generation compatible with unmodified Falcon verification. Do not automatically transfer its compatibility or security analysis to an ETH hash variant.
- The threshold-Falcon artifact's [signing interface](https://github.com/radhika1601/threshold-falcon/blob/master/our_impl/sign.h) and [reference implementation](https://github.com/radhika1601/threshold-falcon/blob/master/falcon_ref/common.c) use the Falcon reference family `2020-09-30` and SHAKE256(nonce40 || message), big-endian 16-bit rejection below 61,445. This matches our round-3 point relation, not FN-DSA framing. Artifact inspection is not a test of MPC-produced signatures in our guest.
- [ZKNOX-HW-FALCON README](https://github.com/ZKNoxHQ/ZKNOX-HW-FALCON/blob/main/README.md). Describes Falcon round-3 signing on Ledger Nano S+ using a low-RAM core, selectable sampler countermeasures and explicit out-of-scope physical attacks. Current core timing tables are host measurements pending replacement by device measurements; legacy device numbers belong to a different implementation.
- The hardware README explicitly uses `FNDSA_FALCON_R3=1` for round-3 adaptation and emits raw s2 for host compression. This project's native C fixtures were not produced by that device.
- [ZKN-PRIVACYHW README](https://github.com/ZKNoxHQ/ZKN-PRIVACYHW/blob/main/README.md). Contains Dilithium/ETHDilithium hardware proof-of-concept applications. It explicitly describes hardcoded keys, development-only code and missing production key derivation. Cite it as feasibility work, not secure wallet deployment evidence.
- [leanVM PR #490](https://github.com/leanEthereum/leanVM/pull/490), “programs: Falcon-512 verification, a proven workload.” Its [guest at head commit](https://github.com/leanEthereum/leanVM/blob/354f7ef2d4a4fee2b9fc3300f93dbc00ec23f7ab/programs/falcon/guest/src/lib.rs) is a `no_std` standard round-3 Falcon-512 verifier for RISC-V. It decodes packed keys and a padded 625-byte signature body in the guest. Our canonical expanded witness model and custom ISA are different. Published PR measurements are not local M4 Pro measurements.

No external publication, forum message or remote repository mutation was performed by this project workflow.

## Aerie extension, checked 4 November 2026

- [Aerie paper, ePrint 2026/2501](https://eprint.iacr.org/2026/2501), Alberto Centelles, Quang Dao, Mohammadtaghi Badakhshan and Justin Thaler; [author-hosted PDF](https://assets.layerzero.network/pdf/aerie.pdf). Section 3 specifies the Falcon relation, Section 6 gives native benchmarks, and Section 7 discusses composition.
- [Aerie v0.2.0 pinned source](https://github.com/a16z/aerie/tree/49b6c212c209286c536196f53618823ffdf0e899): released key-prefixed Falcon-v1.2 profile, verifier-only API, BLAKE2b transcript, public salts, and exact Akita/Jolt/Spongefish dependencies. Local measurements are in the [Aerie extension](aerie-under-leanvm.md); they are not the paper's M4 Max results or full leanVM wrapping measurements.
