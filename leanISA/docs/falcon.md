# ETHFALCON-512 guest

The guest verifies the ETHFALCON-512 relation from the pinned ZKNox reference, using `q=12289`, degree `512`, squared norm bound `34034726`, and its Keccak-256 PRNG. It does not substitute SHAKE256 Falcon, FALZKON, or a small toy polynomial. Inputs come from `vendor/ETHFALCON/test/ethfalcon512-KAT.rsp`; the fixture generator decodes the upstream keys/signatures and checks each signature with an independent Python schoolbook negacyclic-convolution verifier before constructing the witness. The generator also builds the pinned upstream C verifier with `clang -shared -fPIC -O3 -DETHFALCON=1`, placing all build outputs under `build/falcon/`. A source fingerprint controls rebuilding. It verifies the complete upstream signed-message encoding using `crypto_sign_open` and checks that the recovered plaintext matches the KAT. `native_verify_ns_per_signature` records the average per verification over 30 calls after one warmup; `native_C_verify_seconds` and `baseline_native_verify_s` sum those per-record averages for the batch. These measurements include compressed-key/signature decoding and Python ctypes call overhead. The independent Python verifier remains a correctness cross-check, with its timing separately labelled `python_reference_verify_seconds`.

The guest computes the initial seed `Keccak256(salt40 || message)`, then `Keccak256(seed32 || BE64(counter))` for counters starting at zero. Each block is read as sixteen big-endian 16-bit candidates. A candidate below `5*q` is accepted and reduced modulo `q`; all other candidates must be rejected. The first 512 accepted candidates form the challenge polynomial. Forty blocks are available. A signature requiring more blocks is outside this bounded research guest and fails; there is no truncation or host-supplied challenge trusted by the proof.

The signature equation is `s0 = challenge - h*s2` in `Z_q[X]/(X^512+1)`. The guest runs a twisted radix-two NTT for both `h` and `s2`, pointwise multiplication, and the inverse NTT, using a fixed primitive 1024th root. It then centers both signature components, checks each `abs(s0)<=6144` and `abs(s2)<=2047`, and proves `sum(s0_i^2+s2_i^2)<=34034726`. Every such `s2` has a canonical reference compressed encoding. There is no total compressed-payload limit in the guest, matching the pinned upstream `crypto_sign_open`, which checks the complete decoder-consumed length without imposing the signer's output-buffer size. The upstream signer has a 647-byte payload buffer; a previous version of this guest imposed an incorrect 625-byte limit and rejected some valid reference signatures.

## Non-native arithmetic

leanVM's binary-field addition is XOR and is never used as integer addition. A prime-field coefficient `a` is represented as `g^a` in the 64-bit subfield. Integer addition then becomes multiplication of these representations. Every modular result is checked using `g^value = g^remainder * (g^quotient)^q`, with explicit range checks on the quotient and remainder. Variable multiplication uses Boolean exponent bits, reconstructs the exponent, and selects checked square-and-multiply factors. No multiplication, quotient, norm, or polynomial product is accepted merely because the host calculated it.

All modular arithmetic exponents are below `q^2`, and the complete norm is below `1024*6144^2`, well below the generator's `2^64-1` order. Consequently those checked exponent relations cannot hide integer wraparound. The norm upper bound is enforced by a nonnegative, range-checked two-limb complement. Hash words are fully decomposed and reconstructed before their bytes are interpreted as candidates. Every key coefficient and message byte is range checked before hashing.

## Statement and encoding

The public input is an ordered hash-chain commitment. Its initial value is `Keccak256(domain16 || BE64(count))`, where `domain16` is the byte string `pqbench/falcon1` followed by one zero byte. A record contributes `claim = Keccak256(domain16 || key_hash32 || message_hash32)`, and the accumulator becomes `Keccak256(accumulator32 || claim32)`. The guest publishes the final 32-byte accumulator. `message_hash = Keccak256(message)`. `key_hash = Keccak256(LE16(h_0) || ... || LE16(h_511))`, with every coefficient canonical in `[0,q)`.

This is an expanded-key proof codec. The wallet-facing 897-byte NIST public-key blob is decoded by the fixture generator; the guest binds its canonical expanded polynomial, rather than hashing or parsing that blob. The signature witness is its expanded `s2` polynomial and salt, with canonical coefficient and norm checks. Raw compressed-signature bytes are parsed outside the VM and are not themselves part of the public claim. Thus a consumer must use this expanded-key identifier or add an in-VM bridge to its chosen on-chain key encoding. This project does not claim byte-for-byte EIP verifier compatibility.

A program is specialized by batch count and the ordered message-length schedule. Key values, message contents, salts, signatures, and modular witnesses are never compiled into its bytecode. The benchmark schedule consumes distinct upstream KATs up to the available vector count and cycles those vectors for larger counts; message lengths therefore vary across the first vectors. This is a reproducible aggregation workload, not a production transaction generator or a fixed-32-byte wallet-message comparison. Fixture metadata retains the exact vectors and actual compressed signature sizes.

## Checks

`tests/test_falcon.py` exercises independent verification of the first ten upstream Keccak KATs, upstream C verification and rejection of a mutated signed message, valid one- and three-record VM executions, and rejection of bad quotient/remainder hints, malformed key/message ranges, non-Boolean signs, an accepted rejection-sampler candidate, and an out-of-range norm complement. Synthetic signatures with 576- and 640-byte compressed payloads have independently constructed keys making `s0=0`; the upstream C, Python and VM verifiers accept both, including an empty-message case. The host decoder rejects trailing zero bytes, matching the upstream decoder's exact byte-consumption check. A fully recomputed magnitude-2048 signature fails the guest's coefficient range check. Changed-key and changed-message checks recompute the public claim commitment. A zero-signature attack recomputes the complete hash and modular-arithmetic witness and fails the actual norm check. These are regression checks, not a cryptographic audit or a formal proof of the new guest.
