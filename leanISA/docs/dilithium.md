# ethDilithium2 in leanVM

This guest checks the ETH-PRNG variant of Dilithium2 from the pinned `ZKNoxHQ/ETHDILITHIUM` source. It uses the upstream C signer and verifier with `DILITHIUM_MODE=2` and `ETHDILITHIUM=1`, and an independent Python verifier checks every generated input before witness generation. Its parameters are `(n,q,k,l,tau,gamma1,gamma2,omega) = (256,8380417,4,4,39,131072,95232,80)`. Messages are 32 bytes with empty context, formatted as `0x0000 || message` for the upstream signature algorithm. These signatures are not NIST ML-DSA signatures because the upstream ETH variant replaces SHAKE with Keccak-256 counter mode.

The guest verifies the complete signature relation, including challenge sampling and rejected bytes, the signed `z` norm bound, all five forward NTTs, four inverse NTTs, matrix-vector and challenge-key products, hint population, coefficient decomposition, corrected high bits, packing, and the final challenge hash. It checks the signature inside leanVM. Native verification in fixture generation is an independent input check and benchmark baseline, and is not substituted for these constraints.

## Expanded verification keys

The guest uses the same precomputation boundary as upstream `pk_for_eth`: `A_hat`, `NTT(8192*t1)`, and `tr`. The expanded verification key is the registered key identity. The guest does not establish that a supplied expanded key is derived from a separately supplied compact key. A wallet using this experiment must register and authorize the expanded key digest, or separately prove/check expansion at registration. The compact public key in fixture metadata is provenance and supports independent reference verification; it is not the proof's registered key.

The canonical expanded encoding concatenates 4096 `A_hat` residues, 1024 transformed `t1` residues, then 64 bytes of `tr`. Each residue `a` is encoded as the 16-byte little-endian leanVM word `(g^a,0)` with the first eight bytes holding the GF(2^64) generator power and the next eight bytes zero. All residues must lie in `[0,q)`. This experimental encoding is bijective on the allowed range. It occupies 81,984 bytes, compared with the upstream compact key's 1,312 bytes, and its key hash is Keccak-256 of all those bytes. Include that initial registration/distribution cost in wallet comparisons. Upstream compact signatures occupy 2,420 bytes. Guest witnesses use decoded coefficients and a binary hint vector, with all validity bounds checked; the guest does not parse the compact signature's byte encoding.

The statement is an ordered fold. Let `B0 = Keccak256("pq-leanbench/ethdilithium2/v1" padded on the right to 32 bytes with zeroes)`. For each claim in order, `Bi+1 = Keccak256(Bi || expanded_key_hash_i || message_i)`. The two public input words encode the 32-byte final digest in little endian. Count and order are fixed by the guest specialization; this is direct batch proving, not recursive proof merging or set union. A wallet must derive the message from the intended EIP-8141 transaction, chain, nonce, validity window and policy before accepting the claim.

## Non-native arithmetic constraints

leanVM works in characteristic two, where source `+` is XOR. This guest represents integer `a` as `g^a`, with `g` having order `2^64-1`. Multiplication of encoded values adds their integer exponents. Integer modular multiplication is verified by boolean decomposition of the multiplier, bit-selected powers, and the relation `g^(a*b) = g^r * (g^t)^q`, with canonical `r,t` in `[0,q)`. Constant multiplications use the same quotient relation with a compile-time factor. Every exponent in these comparisons is bounded below the generator order, so equality does not admit a wrapped integer relation.

Residue range proofs split both a nonnegative value and its complement to `q-1` into 12-bit and 11-bit digits, constrain every digit with leanVM's bounded exponent range gadget, and check that the encoded value and encoded complement multiply to `g^(q-1)`. Signed norm and rounding bounds similarly use 8-bit and 9-bit digits and an exact bounded complement. Every prover hint is constrained; boolean choices are checked before affecting an arithmetic relation or control flow.

## Run

```sh
PYTHONPATH=python .venv/bin/python -m pqbench.dilithium --count 1 --out build/dilithium/one.json
LEANVM_NUM_THREADS=4 target/release/pq-leanbench execute --input build/dilithium/one.json --report build/dilithium/execute.json
LEANVM_NUM_THREADS=4 target/release/pq-leanbench prove --input build/dilithium/one.json --proof build/dilithium/one.proof --report build/dilithium/prove.json --repeat 1 --warmup 0 --rate 1
target/release/pq-leanbench verify --input build/dilithium/one.json --proof build/dilithium/one.proof
PYTHONPATH=python .venv/bin/python -m unittest discover -s tests -p test_dilithium.py
```

The native shared library is built automatically into `build/dilithium` with `clang` from the pinned C reference. Its filename includes a fingerprint of all compiled C sources and headers, compiler version and compile flags, preventing reuse after source or compiler changes; the full fingerprint, source hash, compiler and revision are retained in fixture metadata. Fixture generation uses random upstream keys and signatures and retains their exact bytes and individual native verification timings. The guest source is fixed for a batch count and does not specialize on those random inputs. Keep each saved fixture when comparing runs. Proofs are currently not zero knowledge, and this guest and its encoding have not been audited.

The challenge sampler expands exactly four Keccak-PRNG output blocks: 128 bytes, including eight sign bytes and at most 120 candidate bytes. It constrains every consumed candidate and requires exactly 39 accepted positions. This creates a completeness cap: a mathematically valid signature needing more than 120 candidate bytes is rejected by this experimental guest and fixture generator. It does not cause acceptance of an invalid signature. Increase the explicitly bounded sampler and rerun source/proof benchmarks if eliminating that cap is required. Matrix expansion in the independent Python input checker also has a bounded 1,200-byte rejection-sampling buffer per polynomial; that host-side bound affects fixture generation only.

At the pinned backend revision, the completed measurements produced and verified a one-signature proof, while a direct two-signature proof failed with `WitnessOutOfRange { log_committed: 29 }`: the native prover currently caps that value at 28. Execution-only measurements for larger batches do not establish that their proofs can be produced. This guest therefore supports measured direct proofs of one signature within the present backend limit; larger direct batches require backend changes or a different guest design. Sharding into one-signature proofs does not itself provide recursive aggregation of those arbitrary guests.

Saved benchmark JSON retains the compact keys, compact signatures and messages in `metadata.records`, allowing exact witness reconstruction without access to a signing secret. `pqbench.dilithium.replay(report_dict)` or `build(count, records=report_dict["metadata"]["records"])` revalidates every compact signature with the pinned C verifier, measures native verification afresh, repeats the independent Python check and reconstructs the original guest source, public input and complete witness. Replay checks the expanded key hash against the saved record when present. Native timing metadata is expected to change between runs.
