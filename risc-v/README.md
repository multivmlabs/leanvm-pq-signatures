# RISC-V implementation

The article uses leanVM's experimental `riscv-exploration` backend at
`06e5c9cd6981103786f9d0a17324241b559a50d3`. See the root
[reproduction guide](../docs/reproduce.md) for setup and commands.

- Falcon uses the pinned upstream guest from leanVM PR #490.
- [ML-DSA-44](mldsa/README.md) uses compact keys/signatures, pure mode and empty context.
- [Raccoon-128](experiments/raccoon-crt32/README.md) uses the measured optimized guest.
- [Raccoon-G](experiments/raccoong-segmented/README.md) uses five linked two-row parts.
- [Native recursion](tree-bench/README.md) aggregates Falcon and ML-DSA batches.

All profiles use 32-byte benchmark messages. Full public-only verification binds
the intended keys/messages and approved program; sender-supplied hashes alone
do not authorize a claim. The receiver invokes complete `Program::verify` or
`Tree::verify`, including remaining polynomial claims.

The article's FORS implementation is [Python leanISA](../leanISA/README.md).
The RISC-V FORS crate remains because the frozen shared runners link it.
The [original Raccoon](raccoon/README.md) and [monolithic G](raccoon-g/README.md)
are retained for the [capacity diagnosis](experiments/raccoon-fit/README.md).

The [capacity recheck](results/reaudit/README.md) explains why the original
32-Falcon/6-ML-DSA prefix boundaries are not universal maxima. Its separate
measurements do not replace the article's original timing series.

Final receipts and raw timing reports are under [results](results). Per-node
proof hashes and sizes remain in those reports; temporary leaf and merge proofs
are regenerated by the runners. [Article figures](../articles/figures/README.md)
are generated from the retained records.
