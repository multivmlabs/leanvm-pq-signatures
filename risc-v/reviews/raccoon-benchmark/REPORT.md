# Independent benchmark review: original Raccoon ports

Reviewed 2026-11-09. Scope: production refusal evidence for the first frozen
Raccoon-128-1 and strict Raccoon-G guests, diagnostic explanations, and preparation
of independent public-receipt checks. This is not a full proof-system audit.

## Current result

The original frozen guests produce **no accepted direct proof** in the tested
prefix corpus. The review independently checked all 64 capacity attempts and all
30 actual direct-prover attempts for each scheme. Every completed capacity report
records the unchanged production `Program::measure` returning `TooLong`; every
direct report additionally records the unchanged `Prover::prove` returning
`TooLong`. All commands completed without a resource-limit abort. The reports
match their frozen runner, guest ELF and backend identities. No `root.proof`
exists for any refused direct point.

This establishes a failure of these executable workloads under this backend's
limits. It is not a statement that the signature schemes cannot be proved or that
their universal maximum batch size is zero. Refusal latency and process RSS must
not be plotted as the time or memory of an accepted proof. There are no proof
bytes to measure for these refused points.

Evidence is [original-rejection-validation.json](original-rejection-validation.json),
generated by the read-only [check_original_refusals.py](check_original_refusals.py).
No workload was rerun by that audit script.

## Why the original workloads are refused

`Program::run` periodically derives padded table heights and checks their complete
committed size while execution is still in progress. `committed_size` refuses a
dimension exceeding `MAX_MU`. That is distinct from the instruction-clock bound:
the latter is `2^35-1`, well above these single-signature executions.

The separate raw-interpreter diagnostic completes each single-signature execution
and checks its expected public output. Its owned public-layout replica reports:

| Original workload | Instructions | Full-layout diagnostic words | Required logarithm |
| --- | ---: | ---: | ---: |
| Raccoon-128-1 | 8,238,032 | 419,337,656 | 29 |
| Raccoon-G strict profile | 19,132,604 | 839,237,560 | 30 |

The unchanged backend supports at most 268,435,456 committed words, dimension 28.
These are **full-execution diagnostic counts**, not accepted production witness
plans, proofs, proof sizes or proving-time measurements. Production refusal
remains the acceptance oracle. The diagnostic uses the unchanged interpreter but
intentionally continues beyond the production allocation guard to explain its
failure. It does not bypass that guard when producing or verifying a proof.

Source review confirms the replica's components correspond to the backend's
table-height, filler-jump, shared-column and first-fit register-packing rules.
The diagnostic's own crosscheck reports agreement with 25 existing production
reports. This reviewer did not present that as a new independent production run.

The largest packed regions are ALU and shifts, not high-half multiplication
alone. Standard Raccoon's ALU packed region is 201,326,592 words; its MULH region
is 35,651,584. Raccoon-G's ALU and SHIFT packed regions are 402,653,184 and
201,326,592 words; MULH is 35,651,584. Removing MULH alone cannot explain the
required savings.

## Independently checked hashing burden

An independent Python `hashlib` oracle counts consumed SHAKE bytes and rejection
samples from the exact first fixture. It reproduces the diagnostic function-call
counts without using its instruction counters:

| Component | Standard Raccoon | Raccoon-G |
| --- | ---: | ---: |
| Public-key hash | 17 | 119 |
| Message hash | 1 | 1 |
| Challenge | 1 | 1 |
| Matrix expansion | 549 | 1756 |
| Commitment hash | 20 | 119 |
| Total Keccak permutations | **588** | **1996** |

The ELF symbol tables were independently parsed: the diagnostic's Keccak address
ranges match the actual 2448-byte functions in both original artifacts. Evidence
is [keccak-symbols.json](keccak-symbols.json) and
[permutation-oracle.json](permutation-oracle.json). The latter is generated by
[permutation_oracle.py](permutation_oracle.py), which executes neither a VM nor
a prover.

The observed software Keccak subtrace accounts for 3,380,412 standard-Raccoon
instructions and 11,475,004 Raccoon-G instructions, approximately 41% and 60% of
their original complete executions. The G Keccak-only subtrace already produces
a 388,777,392-word layout in the same diagnostic. This supports a hashing
bottleneck for this input, kernel and memory configuration. It is not a universal
lower bound for every implementation, accelerator or possible input seed.

## Public proof-consumer checks prepared

The unchanged production direct receiver uses `Program::verify`, which checks
the core proof and settles deferred program claims. The tree receiver uses full
`Tree::verify`, which checks the recursion proof, compares the ordered leaf-output
digest, and settles all terminal dense-polynomial and Flock-matrix claims. Its
public-only path reconstructs every intended pair and canonical repetition of
the final real leaf. It does not load signature witnesses or child proof files.

[binding.py](binding.py) independently derives both profile commitments from raw
bytes using Python BLAKE2s, reconstructs the binary root digest and checks its
location in the protocol-19 proof envelope. This is a public-binding check, not
a replacement for STARK verification.

[consumer_controls.py](consumer_controls.py) is ready to test an unchanged saved
proof with honest and mutated public statements in isolated receiver directories.
It changes first and final public pairs, recomputes their commitments and supplies
fresh caller statement pins. Additional cases cover order, duplicates, count,
program identity, schema, tree shape, rate and malformed root bytes. A G-specific
case changes an unrounded key bit while keeping its rounded verification
coefficient unchanged. These proof-consumer controls have **not** run for the
original guests because no accepted original proof exists.

Any optimized implementation must retain separate source and ELF identities,
undergo its own correctness review and actually produce accepted proofs before
its numbers appear in the article. No capacity cap, verifier check or signature
predicate may be relaxed to manufacture a benchmark point.
